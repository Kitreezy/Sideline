# Sideline

iOS-приложение, которое берёт видео твоих ударов с телефона, вытаскивает скелет
через Vision и показывает, что у тебя гуляет от удара к удару.

Всё считается локально, видео никуда не уходит.

## Запуск

`.xcodeproj` в гите нет — он генерируется из `project.yml` через xcodegen.
После клонирования:

```bash
make bootstrap
```

Скрипт проверит, что xcodegen стоит, заведёт `Configs/Local.xcconfig` из
примера и сгенерирует проект. Дальше впиши в этот конфиг свой
`DEVELOPMENT_TEAM` — без него приложение соберётся, но на устройство не встанет.

```bash
make open     # открыть в Xcode
make test     # тесты на симуляторе, он выбирается сам
make build    # сборка под устройство
make clean    # снести сгенерированный проект
```

`make` пересоздаёт проект сам, если `project.yml` изменился — иначе легко
добавить файл и долго смотреть, почему Xcode его «не видит».

Настройки правятся в `project.yml` и xcconfig, а не в интерфейсе Xcode:
правки в сгенерированном `.xcodeproj` затрутся при следующей генерации.

## Сохранение тренировок

Кэшируется дорогое, пересчитывается дешёвое. На диск идут дорожка скелета
(бинарный plist) и само видео; удары, метрики и выводы считаются при
открытии заново — это миллисекунды. Поэтому после улучшения анализатора
старые тренировки разбираются по-новому без повторного прогона Vision.

Видео перекладывается к приложению до начала разбора: если процесс убьют
в фоне, самое долгое — копирование из галереи — не пропадёт, и при
следующем запуске предложится продолжить. Решения «это не удар» хранятся
отдельно по отпечатку видео и переживают перезапуск.

Лежит всё в Application Support/Sideline/Sessions/<uuid>/. Удаление
тренировки из списка сносит папку вместе с видео.

## Живая камера

Два экрана работают только на устройстве:

- **Проверка кадра** — живой скелет с камеры и вердикт до начала съёмки:
  видно ли игрока целиком, не мелко ли, какой ракурс. Правила в
  `FramingAdvisor`, они покрыты тестами; сама камера — нет.
- **Что тянет камера** — замер, потянет ли телефон запись на высокой частоте
  одновременно с живым разбором позы. От ответа зависит, возможен ли
  гибридный режим (точный файл плюс живой слой).

Живой поток и разбор файла делят один код: `PoseMapping`, `PlayerTracker`,
`CameraViewDetector`. Расхождение между режимами тогда невозможно по построению.

## Демо-тренировка

В отладочной сборке на главном экране есть «Демо-тренировка из синтетики»:
скелет генерируется, мяч подставляется, видео — заглушка. Нужна, чтобы
смотреть интерфейс с ударами, выводами и разделом «на проверку» там, где
Vision не работает.

## Симулятор не годится

Vision body pose в симуляторе не работает вообще: `No available compute device
for VNComputeStageMain`. То же видео даёт 91% кадров со скелетом на маке и 0%
в симуляторе. Проверять можно только на живом устройстве или через CLI ниже.
Приложение отличает это от «человека в кадре нет» и говорит прямо.

## Что происходит, пока идёт разбор

Стадии показываются явно: копирование из галереи (файл приходит только
копией, на большой записи это десятки секунд), поиск ударов, разбор окна
N из M. Оставшееся время оценивается по скорости текущей стадии — у чтения
и у разбора она разная, и смешивать их значит врать в обе стороны.

Экран во время разбора не гаснет, короткое сворачивание переживается.
Настоящего фона на минуты iOS не даёт: примерно через полминуты в свёрнутом
виде процесс остановят, и приложение об этом предупреждает.

## Разбор в два прохода

Модель позы стоит около 7 мс на кадр независимо от содержимого и размера
кадра — это замерено, и это пол. Декодирование — 1 мс, параллельность
даёт 15% (Neural Engine не делится). Единственный настоящий рычаг —
**гнать через Vision меньше кадров**.

Первый проход идёт на 15 кадрах в секунду по уменьшенным до 640 px кадрам:
модель внутри всё равно уменьшает вход, а подать ей маленький — минус
треть времени при 98% найденных скелетов. Он находит окна вокруг всплесков
скорости кисти, с запасом ±1.2 с, чтобы в окно попали замах, проводка
и входящий мяч. Второй проход разбирает эти окна на полной частоте
и полном разрешении, читая каждое окно своим ридером с перемоткой,
а не декодируя всё видео заново.

На живой записи 60 fps: 5.6 минуты — 210 с полным проходом → 133 с,
18.8 минуты — 709 с → 348 с, окна покрывают 33–47% кадров, все настоящие
удары на месте, список подтверждённых мячом тот же. Дальше упирается
в модель: 7 мс на каждый кадр в окнах. Замерять надо на пустой машине —
Neural Engine один, и параллельный прогон тестов растягивает разбор
вдвое-втрое.

Пороги первого прохода заведомо ниже боевых — пропущенный удар потом
не вернуть, а лишнее окно стоит только времени. Списки ударов в обоих
режимах сверяются тестом. Тонкость: порог удара привязан к медианной
скорости кисти, а в дорожке после второго прохода остаются одни удары,
и медиана по ним фоном уже не является. Поэтому фон замеряется на первом
проходе, по всей записи, и передаётся дальше отдельно.

## Прогон видео с мака

```bash
./Tools/analyze.sh ~/Desktop/тренировка.mov right
```

Флаг `--full` заставляет разобрать все кадры, `--force` — включить два прохода
там, где эвристика их отключает. Оба нужны, чтобы сравнивать режимы.
`--noise <от> <до>` — разброс метрик на отрезке, где игрок стоит: шум
измерения, который нельзя приписывать технике. `--export <папка>` — сессия
в формате приложения: подложить в контейнер симулятора вместе с видео
(`video.mov`) и смотреть интерфейс на живых данных там, где Vision не работает.

Печатает найденные удары, разброс метрик и устойчивость трекинга. Пороги
подкручиваются по живым видео именно так — симулятор для этого слишком медленный.

## Что важно понимать про точность

**Контакт: по мячу, если он пойман, иначе по максимуму скорости кисти.**
Третий проход гоняет `DetectTrajectoriesRequest` в окнах вокруг найденных
ударов. Мяч от руки и ракетки отличается одним признаком: он прилетает
издалека и обрывается у кисти *до* пика скорости — обод ракетки тоже приходит
издалека, но заканчивает путь в проводке, после пика. Пойманный мяч даёт
контакт как измерение, а не оценку, и снимает сомнения по форме движения.

На дальней съёмке мяч в 12 пикселей ловится через раз. Поэтому политика
такая: если мяч на записи ловится (от пяти подтверждений), взмахи без мяча
уходят в раздел «на проверку» и в статистику не идут — на живой записи
по форме движения они почти все оказались ложными, стоящий игрок
с ракеткой по скелету неотличим от бьющего. Если мяч не пойман ни разу
(яркий фон, слишком далеко), форма остаётся единственным судьёй.

Каждый удар в списке идёт с кадром контакта, кадрированным вокруг игрока
по скелету: один взгляд отвечает на вопрос «удар это или нет» быстрее любой
метрики, и проверка двадцати кандидатов занимает минуту. Свайп — вернуть
или выкинуть. В разборе удара видео приближается к игроку по тому же
прямоугольнику — на съёмке с задней линии без этого его не разглядеть.

**Эталона нет.** Первая версия сравнивает тебя только с тобой же: насколько
удар №7 похож на удар №12. Это сознательный выбор — разброс собственных
показателей информативен сам по себе и не требует спорных «правильных» порогов.
Разброс считается отдельно по каждому типу удара: смешивать форхенды
с бэкхендами бессмысленно.

**Цифры переводятся в выводы.** Голые числа для того, кто учится,
бесполезны. Поэтому по каждому типу удара показывается «над чем работать» —
не больше трёх пунктов, ранжированных — из трёх источников:

- *разброс* переводится в теннисное следствие: «локоть на контакте гуляет
  на ±29° — отсюда нестабильная глубина и направление»;
- *ориентиры из тренерской практики* с направлением, а не точкой: «контакт
  0.1 корпуса впереди, тренеры советуют 0.3–0.7 — опаздываешь». Это
  не измеренная норма, и в интерфейсе так и подписано; но направление
  «контакт впереди — хорошо» не спорно ни у одного тренера;
- *лучшие удары против худших*: серия делится по скорости кисти на трети,
  и ищется метрика, которая между ними расходится сильнее всего. Сравнение
  только с самим игроком, без чужих норм.

К каждому пункту — что делать на корте. Плюс одна самая стабильная метрика,
чтобы было видно, на что опереться. Ниже 5 ударов выводов нет: это гадание.
Ориентиры и подсказки — `MetricGuidance`, ранжирование — `InsightEngine`.

**Не всё, что разгоняет кисть, — удар.** Сплит-степ, перехват ракетки,
подбор мяча дают такой же всплеск скорости. Каждый найденный всплеск
проверяется по форме движения: кисть должна пройти заметный путь от конца
замаха до контакта, идти по дуге, а не петлять, и пик должен быть выше фона.
Не прошедшие проверку показываются отдельно с причиной и в статистику не идут.
Пользователь может вернуть удар или выкинуть — он видит запись, ему виднее;
решения запоминаются для этого видео. Пороги (`StrokeAnalyzer.Tuning`)
выставлены из геометрии и на живой записи пока не проверены.

**Ракурс определяется сам, но не все метрики переносятся.** Съёмка сбоку
остаётся рекомендованной, потому что только в ней доступен полный набор.
При съёмке сзади или спереди метрики, которым нужна глубина, отключаются —
показать их значило бы показать число, которое меряет не то, что написано.

| Метрика | Сбоку | Сзади / спереди |
|---|---|---|
| Скорость кисти, высота контакта, углы, тайминги | да | да |
| Контакт впереди корпуса | да | нет, это глубина |
| Разворот плеч, разделение плечи/таз | да | нет, разворот не виден как наклон |

**Всё меряется в длинах корпуса, а не в пикселях — покадрово.** Игрок ходит
по корту и подходит к камере, его размер в кадре меняется втрое; одна медиана
на всё видео превращала шаг у камеры в «удар». Масштаб берётся из каждого
кадра и сильно сглаживается, чтобы замах не читался как приближение.

## Устройство

- `Sources/StrokeKit` — вся логика, без единого импорта SwiftUI
  - `PoseExtractor` — видео → скелет по кадрам (AVAssetReader + Vision)
  - `Signal` / `SignalProcessing` — интерполяция пропусков, сглаживание, производные, поиск пиков
  - `StrokeAnalyzer` — нарезка на удары, фазы, метрики
  - `Metrics` — что меряем и как это читать
- `Sources/Sideline` — SwiftUI поверх этого
- `Tests/StrokeKitTests` — синтетические удары с заранее известным моментом контакта

Логика отделена от UI намеренно: алгоритм придётся крутить по живым видео,
и делать это через симулятор больно.

## Известные упрощения

- Тип удара определяется по тому, какое плечо развёрнуто вперёд: на форхенде
  небьющее, на бэкхенде бьющее. Удар над головой ловится по тому, насколько
  кисть выше шеи. Пороги откалиброваны по одной записи — на своей съёмке
  их наверняка придётся двигать.
- Разворот плеч меряется по наклону линии плеч в 2D. Вне съёмки сбоку метрика
  вырождается и потому отключается. Чтобы она работала в любом ракурсе,
  нужен переход на `DetectHumanBodyPose3DRequest`.
- Игрок ведётся по трассе: в каждом кадре выбирается тот, кто ближе к игроку
  из предыдущего кадра, а «самый крупный» используется только на первом кадре
  и после потери. Парная игра всё равно развалится.
- Смонтированные ролики (нарезки с YouTube) анализировать нельзя: разные
  ракурсы и разные игроки смешиваются в одну статистику. Разрывы детектируются
  и выбрасываются, и приложение об этом предупреждает, но цифры всё равно
  бессмысленны.
- `joint(for:)` из свежего Vision SDK не используется: символа нет в рантаймах
  iOS 18.x, приложение падало бы при запуске. Везде `allJoints()`.

## Что показала первая живая запись

Тренировка 5.6 минуты, 60 fps, телефон на полу у задней линии: игрок
занимает 4% высоты кадра. Скелет в розыгрышах виден в 96% кадров
с уверенностью 0.77 — этого хватает. Но 47% времени игрок ходит за мячами,
стоит и подходит к камере, и именно там рождаются ложные удары: по форме
движения они неотличимы от настоящих. Мяч ловится примерно в половине
настоящих ударов; когда пойман, контакт совпадает с кадром, где мяч
на струнах, с точностью до 0.05–0.15 с. Помощник по кадрированию такую
съёмку забраковал бы: порог «слишком мелко» — 8%.

## Что дальше

1. Снять контрольное видео по инструкции из приложения (одна камера сбоку,
   один игрок, 15–20 ударов) и подкрутить `StrokeAnalyzer.Tuning` по нему.
   Сейчас пороги проверены на синтетике и на одной чужой нарезке.
2. Прогресс между тренировками: сессии уже хранятся, осталось сравнивать.
3. Переход на 3D-позу (`DetectHumanBodyPose3DRequest`), чтобы метрики глубины
   работали в любом ракурсе.
4. Сравнение с эталонным видео (выравнивание по фазам через DTW).
