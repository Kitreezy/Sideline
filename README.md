# Разбор удара

iOS-приложение, которое берёт видео твоих ударов с телефона, вытаскивает скелет
через Vision и показывает, что у тебя гуляет от удара к удару.

Всё считается локально, видео никуда не уходит.

## Запуск

`.xcodeproj` в гите нет — он генерируется из `project.yml` через xcodegen.
После клонирования:

```bash
make bootstrap
```

Скрипт проверит, что xcodegen стоит, заведёт `Configs/Local.xcconfig` из
примера и сгенерирует проект. Дальше впиши в этот конфиг свой
`DEVELOPMENT_TEAM` — без него приложение соберётся, но на устройство не встанет.

```bash
make open     # открыть в Xcode
make test     # тесты на симуляторе, он выбирается сам
make build    # сборка под устройство
make clean    # снести сгенерированный проект
```

`make` пересоздаёт проект сам, если `project.yml` изменился — иначе легко
добавить файл и долго смотреть, почему Xcode его «не видит».

Настройки правятся в `project.yml` и xcconfig, а не в интерфейсе Xcode:
правки в сгенерированном `.xcodeproj` затрутся при следующей генерации.

## Живая камера

Два экрана работают только на устройстве:

- **Проверка кадра** — живой скелет с камеры и вердикт до начала съёмки:
  видно ли игрока целиком, не мелко ли, какой ракурс. Правила в
  `FramingAdvisor`, они покрыты тестами; сама камера — нет.
- **Что тянет камера** — замер, потянет ли телефон запись на высокой частоте
  одновременно с живым разбором позы. От ответа зависит, возможен ли
  гибридный режим (точный файл плюс живой слой).

Живой поток и разбор файла делят один код: `PoseMapping`, `PlayerTracker`,
`CameraViewDetector`. Расхождение между режимами тогда невозможно по построению.

## Симулятор не годится

Vision body pose в симуляторе не работает вообще: `No available compute device
for VNComputeStageMain`. То же видео даёт 91% кадров со скелетом на маке и 0%
в симуляторе. Проверять можно только на живом устройстве или через CLI ниже.
Приложение отличает это от «человека в кадре нет» и говорит прямо.

## Что происходит, пока идёт разбор

Стадии показываются явно: копирование из галереи (файл приходит только
копией, на большой записи это десятки секунд), поиск ударов, разбор окна
N из M. Оставшееся время оценивается по скорости текущей стадии — у чтения
и у разбора она разная, и смешивать их значит врать в обе стороны.

Экран во время разбора не гаснет, короткое сворачивание переживается.
Настоящего фона на минуты iOS не даёт: примерно через полминуты в свёрнутом
виде процесс остановят, и приложение об этом предупреждает.

## Разбор в два прохода

Vision стоит около 9 мс на кадр независимо от содержимого. Запись серии
в слоу-мо — это десятки тысяч кадров и минуты ожидания, хотя сами удары
занимают малую долю времени.

Первый проход идёт по прореженным кадрам и находит окна всплесков, второй
разбирает на полной частоте только их. Точность контакта не страдает:
внутри окон обрабатывается каждый кадр.

Выигрыш считается как `1/stride + доля времени под окнами`:

| Съёмка | stride | Под окнами | Итого |
|---|---|---|---|
| 240 fps, тренировка с паузами | 8 | ~20% | ~30% работы |
| 240 fps, плотный обмен | 8 | ~75% | ~88%, почти без выигрыша |
| 60 fps | 2 | — | отключается: первый проход съедает экономию |

То есть режим окупается на слоу-мо с паузами — ровно там, где полный проход
и невыносим. На обычных 60 fps он отключается сам, потому что при stride 2
разбор выходит дороже одного прохода (проверено: 29 с против 24 с).

Списки найденных ударов в обоих режимах совпадают — сверено на записи
и закрыто тестом. Тонкость: порог удара привязан к медианной скорости кисти,
а в дорожке после второго прохода остаются одни удары, и медиана по ним
фоном уже не является. Поэтому фон замеряется на первом проходе, по всей
записи, и передаётся дальше отдельно. Без этого терялись слабые удары.

## Прогон видео с мака

```bash
./Tools/analyze.sh ~/Desktop/тренировка.mov right
```

Флаг `--full` заставляет разобрать все кадры, `--force` — включить два прохода
там, где эвристика их отключает. Оба нужны, чтобы сравнивать режимы.

Печатает найденные удары, разброс метрик и устойчивость трекинга. Пороги
подкручиваются по живым видео именно так — симулятор для этого слишком медленный.

## Что важно понимать про точность

**Момент контакта определяется по максимуму скорости кисти, а не по мячу.**
Мяч не отслеживается вообще. Проверено на записи тренировки Алькараса
(60 fps, вид сзади): на двух проверенных ударах оценка попала в кадр, где мяч
физически лежит на струнах. Но это всё равно оценка, а не измерение: на 30 fps
это ±33 мс, о чём приложение честно предупреждает.

**Эталона нет.** Первая версия сравнивает тебя только с тобой же: насколько
удар №7 похож на удар №12. Это сознательный выбор — разброс собственных
показателей информативен сам по себе и не требует спорных «правильных» порогов.
Разброс считается отдельно по каждому типу удара: смешивать форхенды
с бэкхендами бессмысленно.

**Не всё, что разгоняет кисть, — удар.** Сплит-степ, перехват ракетки,
подбор мяча дают такой же всплеск скорости. Каждый найденный всплеск
проверяется по форме движения: кисть должна пройти заметный путь от конца
замаха до контакта, идти по дуге, а не петлять, и пик должен быть выше фона.
Не прошедшие проверку показываются отдельно с причиной и в статистику не идут.
Пользователь может вернуть удар или выкинуть — он видит запись, ему виднее;
решения запоминаются для этого видео. Пороги (`StrokeAnalyzer.Tuning`)
выставлены из геометрии и на живой записи пока не проверены.

**Ракурс определяется сам, но не все метрики переносятся.** Съёмка сбоку
остаётся рекомендованной, потому что только в ней доступен полный набор.
При съёмке сзади или спереди метрики, которым нужна глубина, отключаются —
показать их значило бы показать число, которое меряет не то, что написано.

| Метрика | Сбоку | Сзади / спереди |
|---|---|---|
| Скорость кисти, высота контакта, углы, тайминги | да | да |
| Контакт впереди корпуса | да | нет, это глубина |
| Разворот плеч, разделение плечи/таз | да | нет, разворот не виден как наклон |

**Всё меряется в длинах корпуса, а не в пикселях.** Поэтому цифры не зависят от
того, как далеко стоит камера (на это есть тест).

## Устройство

- `Sources/StrokeKit` — вся логика, без единого импорта SwiftUI
  - `PoseExtractor` — видео → скелет по кадрам (AVAssetReader + Vision)
  - `Signal` / `SignalProcessing` — интерполяция пропусков, сглаживание, производные, поиск пиков
  - `StrokeAnalyzer` — нарезка на удары, фазы, метрики
  - `Metrics` — что меряем и как это читать
- `Sources/TennisForm` — SwiftUI поверх этого
- `Tests/StrokeKitTests` — синтетические удары с заранее известным моментом контакта

Логика отделена от UI намеренно: алгоритм придётся крутить по живым видео,
и делать это через симулятор больно.

## Известные упрощения

- Тип удара определяется по тому, какое плечо развёрнуто вперёд: на форхенде
  небьющее, на бэкхенде бьющее. Удар над головой ловится по тому, насколько
  кисть выше шеи. Пороги откалиброваны по одной записи — на своей съёмке
  их наверняка придётся двигать.
- Разворот плеч меряется по наклону линии плеч в 2D. Вне съёмки сбоку метрика
  вырождается и потому отключается. Чтобы она работала в любом ракурсе,
  нужен переход на `DetectHumanBodyPose3DRequest`.
- Игрок ведётся по трассе: в каждом кадре выбирается тот, кто ближе к игроку
  из предыдущего кадра, а «самый крупный» используется только на первом кадре
  и после потери. Парная игра всё равно развалится.
- Смонтированные ролики (нарезки с YouTube) анализировать нельзя: разные
  ракурсы и разные игроки смешиваются в одну статистику. Разрывы детектируются
  и выбрасываются, и приложение об этом предупреждает, но цифры всё равно
  бессмысленны.
- `joint(for:)` из свежего Vision SDK не используется: символа нет в рантаймах
  iOS 18.x, приложение падало бы при запуске. Везде `allJoints()`.

## Что дальше

1. Снять контрольное видео по инструкции из приложения (одна камера сбоку,
   один игрок, 15–20 ударов) и подкрутить `StrokeAnalyzer.Tuning` по нему.
   Сейчас пороги проверены на синтетике и на одной чужой нарезке.
2. Сохранение сессий, чтобы видеть прогресс между тренировками.
3. Переход на 3D-позу (`DetectHumanBodyPose3DRequest`), чтобы метрики глубины
   работали в любом ракурсе.
4. Сравнение с эталонным видео (выравнивание по фазам через DTW).
